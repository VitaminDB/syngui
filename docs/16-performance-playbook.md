# Ускорение приложений на syngui

Разбор работы 12.09.2026: жалоба «чат виснет при 30–70 сообщениях» разложилась
на пять независимых причин, четыре из которых были общими для всего
фреймворка. Здесь — что уже починено в ядре, что нужно делать в каждом
приложении и какие грабли проверены на практике.

Главное правило: **сначала замер, потом правка**. Половина «очевидных»
причин в этой работе оказалась неверной (например, лента якобы
пересобиралась на каждый токен — нет; стрим тормозил не разбором markdown, а
отрисовкой).

## 1. Инструменты замера

- `syngui::perf::counters` — счётчики за интервал: созданные и удалённые
  элементы, пересборки `Reactive`, разборы markdown (вызовы и байты), вызовы
  подсветки, проходы `rebuild_if_needed`, построения индекса стилей,
  «настоящие» обновления MarkdownView, число слотов сигналов.
  `snapshot()` / `since(&earlier)` / `Display`.
- `TestHarness::frame(engine, w, h) -> FrameTimings` — полный кадр приложения
  (пересборка со стилями, эффекты, раскладка, повторная пересборка, a11y,
  display list) с временем фаз.
- Образцы бенчей: `synthos/src/pages/syn_chat/feed_bench.rs` (лента чата) и
  `synthos/src/pages/notes/doc_bench.rs` (документ заметки). Запуск:
  `cargo test -p synthos --features testing --lib feed_bench -- --ignored --nocapture --test-threads=1`.
- В живом приложении: `MGUI_PROFILE=1`, F12 (devtools, число элементов).
- Ловушка: в харнессе нет GPU, значит нет атласа шрифтов — текст меряется
  оценкой, поэтому абсолютные миллисекунды ниже реальных, а число элементов,
  пересборок, разборов и подсветок — точное. Сравнивать «до/после», а не с
  живым приложением.

## 2. Что уже исправлено в ядре (достаётся всем приложениям даром)

1. **Обратный индекс подписок** (`signal.rs`). Отписка (`begin_tracking` на
   каждой пересборке `Reactive`, `cleanup_element` при удалении) перебирала
   ВСЕ слоты сигналов приложения. Слоты не освобождаются, поэтому цена росла
   за сессию. Теперь runtime помнит, какие слоты читал элемент.
2. **Кэш индекса правил MSS** (`mss/cascade.rs`). `RuleIndex::build` шёл по
   всему stylesheet при каждом `apply_styles`, а кадр с пересборкой зовёт его
   до девяти раз. Теперь индекс строится раз на версию таблицы стилей
   (`StyleEngine::stylesheet_version`, новая версия при загрузке и дополнении).
3. **Кэш разбора markdown** (`parse_markdown_cached`, LRU по содержимому) и
   **`MarkdownView::update` без работы**, когда документ и настройки те же:
   не перемеряет, не сбрасывает выделение и меню. Сигналы контекстного меню
   переехали из конструктора виджета в элемент.
4. **Кэш подсветки кода** (`highlight_cached`, LRU по коду, языку и теме).
   Раньше syntect гонялся в каждом кадре по каждому видимому блоку.
5. **Отсечение блоков в `MarkdownView`**: раскладка запоминает высоты
   верхнеуровневых блоков, отрисовка пропускает то, что за пределами видимой
   области. Длинный документ перестал стоить как целиком видимый.
6. **`RwSignal::with` / `with_untracked`** — чтение значения по ссылке без
   клона (значение вынимается на время замыкания и возвращается, поэтому
   внутри можно трогать другие сигналы).
7. **Сверка детей по ключам** (`Widget::widget_key`) и виджет **`Keyed`**:
   вставка и удаление в середине списка перестают пересоздавать соседей, а
   при неизменной версии строки её сборщик не вызывается вовсе.
8. **`VirtualList`** — список с переменной высотой строк: высоты по ключу,
   префиксные суммы, якорь по первой видимой строке, `follow_end`,
   `reset_key`, `scroll_to(key, generation)`.

## 3. Чек-лист для каждого приложения

### 3.1. Ничего блокирующего в сборке виджета

Сборка идёт в кадре. Любой синхронный ввод-вывод в ней — это фриз всего
интерфейса, причём на каждой пересборке, а не один раз.

Найденные примеры: перебор звуковых устройств (`cpal` → ALSA) — **950 мс**;
сканирование каталога моделей с чтением архитектуры бандлов — 155 мс;
чтение JSON чата с диска ради одного поля; хэш всей истории на каждое
изменение.

Как искать: `grep -n "read_dir\|File::open\|fs::read\|Command::new\|list_.*devices\|\.metadata()"`
по файлам страниц; всё, что вызывается внутри `view()`, `Reactive::new(...)`
или замыкания `.child(move || ...)`.

Шаблон замены — опрос в фоне, результат в сигнал:

```rust
pub fn scan_input_devices(ctx: &AudioCtx, force: bool) {
    static BUSY: AtomicBool = AtomicBool::new(false);
    if !force && ctx.input_devices.get_untracked().is_some() { return; }
    if BUSY.swap(true, Ordering::SeqCst) { return; }
    let devices = ctx.input_devices;
    std::thread::spawn(move || {                    // обычный поток: вызов блокирующий
        let list = syngui::audio::list_input_devices();
        syngui::async_runtime::run_on_main_thread(move || {
            devices.set(Some(list));
            BUSY.store(false, Ordering::SeqCst);
        });
    });
}
```

В UI: пока `None` — показывать сохранённое значение, рядом кнопка «обновить»
с `force = true`.

### 3.2. Подписки

- `signal.get()` клонирует значение целиком. Если нужен флаг или длина —
  `with` / `with_untracked`.
- Читать сигнал в сборке значит подписать на него весь узел. Проверять, что
  в сборке списка не читается то, что меняется часто (например `pending`
  всей страницы) — иначе перестраивается весь список.
- Карты состояния (что раскрыто) — общие сигналы: клик по одной строке
  будит всех подписчиков. Лечится тем, что состояние строки входит в её
  версию (см. 3.3), а сама карта читается на уровне списка.

### 3.3. Длинные списки

Порядок внедрения, каждый шаг даёт эффект сам по себе:

1. **Модель строк**: из данных получается `Vec<Row { key, version, kind }>`.
   `key` — стабильный идентификатор (не индекс!), `version` — хэш всего, от
   чего зависит вид строки. Образец: `synthos/src/pages/syn_chat/lane.rs`.
   В версию обязаны входить и те флаги, которые сборщик строки читает без
   подписки (у чата это «карточка — хвост ленты» и «визард отвечен»), иначе
   мемоизированная строка застынет. Но привязывать такие флаги надо к тем
   строкам, которые их читают, иначе каждое добавление элемента обесценит
   весь список.
2. **`Keyed`**: каждая строка оборачивается в `Keyed::new(key, version, builder)`.
   Сборщик вызывается, только если версия изменилась.
3. **`VirtualList`**: строит только видимое окно.
   ```rust
   VirtualList::new(rows)            // rows: Vec<VirtualRow>
       .gap(14.0)
       .estimated_row_height(170.0)  // средняя высота строки
       .overscan(900.0)              // запас за краями, px
       .follow_end(true)             // лента: держаться низа
       .reset_key(hash(document_id)) // смена документа сбрасывает высоты и смещение
       .scroll_to(key, generation)   // переход к строке (поиск)
   ```
   Ключи должны быть уникальны: элемент, который сам себе строит ключ, обязан
   дедуплицировать (у чата — номер вхождения). Если ключ есть не у всех детей
   уровня или есть дубликаты, ядро молча откатывается на позиционную сверку.

### 3.4. Живое состояние вне виджета

Строка вне окна размонтирована. Всё, что должно пережить это, обязано жить
снаружи:

- плееры и декодированный звук — в реестре по стабильному ключу (у чата —
  sha вложения), уборка не трогает то, что играет; полная остановка —
  отдельным вызовом при смене документа;
- черновики полей ввода — в контексте, парой (ключ строки, текст): иначе
  `MultilineTextEdit::update` затрёт набранное;
- раскрытость блоков, выбор, подсветка — в сигналах-картах по стабильному
  ключу.

### 3.5. Диск и автосейв — с кадра

Эффекты выполняются внутри кадра, перед раскладкой. Запись файла там — это
фриз. Шаблон: эффект только отмечает правку; таймер с дебаунсом (и потолком
ожидания) снимает снимок; сериализация и запись — в фоновом потоке с очередью
по файлу (порядок сохраняется, незабранный снимок заменяется следующим,
замена файла атомарная через `tmp` + `rename`); принудительный сброс при
смене документа, архивации, выходе и перед операциями, которые читают файл.
Образец: `synthos/src/syn_chat/autosave.rs` + очередь в `storage.rs`.

### 3.6. Анимации и мелочи

- Свой `Element::animate` тикает только при заявке `wants_animate_tick`.
- Keyframes MSS работают только у `DecoratedBox` и `MapView`; на `Text`,
  `ToolButton`, `Icon` свойство `animation` молча игнорируется.
- Анимация появления (`pop-in`) на строках списка: после виртуализации она
  проигрывается каждый раз, когда строка возвращается в окно. Держать её
  классом, который выдаётся только действительно новым строкам.

## 4. Симптом → где смотреть

| Симптом | Вероятная причина | Что проверить |
|---|---|---|
| Страница открывается с фризом в 0,5–1 с | блокирующий вызов в сборке | `grep read_dir/File::open/list_*devices` по странице |
| Лаг растёт к концу сессии | утечка слотов сигналов и O(S)-отписка | счётчик `slots` в снимке |
| Ввод символа тормозит в длинном документе | пересборка/перемер всего | `пересб` и `раскл` в `FrameTimings` |
| Прокрутка рвётся | отрисовка всего содержимого | `отрис` в фазах, счётчик `hl` |
| Каждое событие «дорогое» независимо от того, что изменилось | пересоздание детей позиционной сверкой | `elem +N -N` в счётчиках |
| Кадр дорожает с числом элементов, хотя менялось одно | O(E)-проходы: стили, a11y, позиционирование | `стили`/`a11y`, `элементов` |

## 5. Проверенные грабли

- **Отсечение markdown и выделение.** Позиции выделения — индексы в списке
  участков, который собирается прямо при отрисовке. Пропуск блоков сдвинул бы
  их, поэтому при активном выделении отсечение выключается.
- **Сигналы привязаны к потоку.** В тестах: `drain_main_thread_callbacks()`
  выполняет и чужие колбэки, а у другого потока свои слоты с теми же
  номерами — чтение падает с «signal type mismatch». Такие тесты запускать
  отдельно в один поток.
- **`ElementId` уникален внутри дерева, а не глобально** (`ElementTree` выдаёт
  свои номера). Глобальная уборка по id между окнами опасна.
- **`.class()` меняет тип виджета** (`StyledWidget<W>`). Если строка списка в
  одном состоянии с классом, а в другом без — тип «прыгает» и элемент
  пересоздаётся вместе с состоянием. Ставить класс всегда, менять значение.
- **`TestHarness` строит дерево только на `rebuild()`/`frame()`**, а не в
  `new()`. Первый замер легко снять не с того места.
- **`Keyed` обязан перенимать новый сборщик даже при той же версии**: иначе
  пересборка по сигналу построит строку из устаревшего снимка данных.
- **`VirtualList` при смене документа переиспользуется** (позиционная сверка
  отдаёт тот же элемент) — без `reset_key` новый документ откроется на
  смещении старого.
- **Сборки:** одна за раз. Несколько параллельных `cargo` подвешивают машину
  (проверено), ядра при этом ограничивать не нужно.

## 6. Числа для калибровки (debug, синтетика)

Лента чата на 300 сообщений, было → стало:

| Сценарий | Было | Стало |
|---|---|---|
| Открытие чата | 1161 мс | 23 мс |
| Событие агентного хода (tool_result) | 3375 мс | 5,8 мс |
| Конец хода | 3076 мс | 6,4 мс |
| Кадр стрима длинного ответа (10 КБ) | 30,3 мс (пики 100) | 2,7 мс |
| Кадр прокрутки | 47,4 мс | 0,56 мс |
| Элементов в дереве | 8483 | 312 |

Документ заметки на 300 блоков (после правок ядра, без виртуализации):
открытие 8,5 мс, набор символа 3,8 мс, прокрутка 0,06 мс, 853 элемента —
виртуализация там не нужна. Разница с чатом в том, что пузырёк тяжелее блока
на порядок: мерить, а не предполагать.
